<objective>
Give the medallion a cycle identity and honest per-phase durations, so the optimisations
in later plans can be measured rather than asserted.

Purpose: today one logical cycle emits two records under the same `source`/`status`
identity, and the outer `silver_duration_ms` strictly contains the nested B2 duration —
so `sum(silver_duration_ms)` over a window over-counts, which already misled one
investigation. This plan makes each phase measurable on its own, which is what makes
SHD-01 and GLD-01 provable: the `shadow` phase duration is exactly the number SHD-01
drives toward zero, and the `gold` phase duration is exactly what GLD-01 targets.

Output: `cycle_id` threaded through `run` / `_run_m4` / `_run_legacy` / `run_b2`;
`b2`, `shadow`, `gold` and `cycle` records; non-overlapping durations; snapshot ids; and
a `B2Outcome` roll-up so the cycle record carries the physical-cost values the Prometheus
gauges were previously being reset to zero with.

**Locked constraints carried in:** `silver_duration_ms` and `gold_duration_ms` stay
populated **only on the `cycle` row**, keeping today's inclusive meaning, so historical
rows remain byte-for-byte interpretable and `cycle_id IS NULL` cleanly separates the two
eras. Never reuse those two columns for a phase-scoped value.
</objective>

  <action>
Thread a cycle identity and re-base the timers.

**Identity.** Add `cycle_id: str | None = None` as a keyword-only parameter to `run`,
`_run_m4`, `_run_legacy` and `run_b2`. `run` generates `uuid.uuid4().hex` when none is
supplied and passes it to whichever branch it selects; `_run_m4` and `_run_legacy` pass
it into `run_b2` and into every `metrics.record` call. `run_b2` generates its own when
called directly with none, so its existing direct-call unit tests keep working
unchanged. Also add `fs: S3FileSystem | None = None` to `run` and `_run_m4` and pass it
through to `run_b2`; do **not** call `get_fs()` eagerly anywhere in `_run_m4` — the
in-memory doubles used by `tests/features/test_shadow_cutover.py` must never cause a
real `S3FileSystem` to be constructed or contacted.

**Phase segmentation.** In `_run_m4`, capture `t0` at entry (already present as
`started`), `t_b2_start` immediately before the `run_b2` call, `t_b2_end` immediately
after it, and reuse the existing `gold_started` as `t_gold_start` and the existing end
timestamp as `t3`. Then:

- the `b2` record is the one `run_b2` already emits, now carrying
  `phase="b2"` and `cycle_id`, with its own internal timer in `duration_ms` and
  `silver_duration_ms` **removed** from that call;
- a new `shadow` record is emitted by `_run_m4` with
  `duration_ms = (t_gold_start - t0) - (t_b2_end - t_b2_start)`, i.e. the whole pre-Gold
  segment minus the incremental writer's window: the pinned Bronze scan, the legacy
  rebuild, the persisted-Silver read and the comparison;
- a new `gold` record is emitted with `duration_ms = t3 - t_gold_start`;
- the existing outer record becomes the `cycle` record with `duration_ms = t3 - t0` and
  keeps `silver_duration_ms = t_gold_start - t0` and `gold_duration_ms = t3 - t_gold_start`
  with exactly today's inclusive meaning.

Because `run_b2`'s own timer starts after it loads progress, the outbox listing and the
completion ledger, `b2 + shadow + gold` is **less than or equal to** the cycle, and the
residual is the writer's own state-load preamble, which is deliberately attributed to no
phase. State that in a comment next to the subtraction — it is the one place a reader
would otherwise assume an arithmetic bug.

For the `_run_m4` legacy branch (`selected_mode == "legacy"`), no `b2` record exists and
the legacy Silver build falls inside the `shadow` segment. Note in the same comment that
this branch is **unreachable under any accepted rollout state** — `RUNTIME_ROLLOUT_MATRIX`
admits `SILVER_MODE=legacy` only as `("legacy","legacy","0")`, which `run` routes to
`_run_legacy` — so that attribution is a test-only artefact and not an operational claim.

**Snapshot identity.** Record `silver_snapshot_id` on the `b2` record (the Silver
snapshot after the B2 work), `bronze_snapshot_id` and `silver_snapshot_id` on the
`shadow` record, `silver_snapshot_id` and `gold_snapshot_id` on the `gold` record, and
all three on the `cycle` record. Reuse the existing `_snapshot_id` helper, which already
tolerates doubles that lack `current_snapshot`. Change
`_read_persisted_silver(catalog)` to return `(rows, snapshot_id)` — it is referenced
nowhere in `tests/`, so the signature is free.

**Roll-up.** Add a frozen dataclass `B2Outcome` with the fields `duration_ms`,
`silver_rows`, `files_processed`, `keys_processed`, `lower_versions_ignored`,
`ff14_conflicts`, `work_available`, `work_in_flight`, `work_completed`, `files_planned`,
`bytes_planned`, `files_removed`, `files_added`, `bytes_removed`, `bytes_added`,
`snapshot_delta`, `silver_snapshot_id`. `run_b2` returns it alongside emitting its own
record. `_run_m4` passes the physical-cost fields into the `cycle` record so
`lakehouse_files{kind="planned"}`, `lakehouse_bytes`, `lakehouse_processed{kind="keys"}`
and `lakehouse_work{...}` stop being published as zeros. A `None` return must be handled
as an all-zero roll-up: `tests/test_m4_gold.py` and
`tests/features/test_shadow_cutover.py` both stub `run_b2` to return `None`.

Do not change `compare_business_state`, `build_silver`, `build_gold`, the B2 resolution
algorithm, FF-14 handling, `_pin_bronze_boundary`'s pinning semantics, or
`RUNTIME_ROLLOUT_MATRIX`. This plan adds no skip and removes no work.
