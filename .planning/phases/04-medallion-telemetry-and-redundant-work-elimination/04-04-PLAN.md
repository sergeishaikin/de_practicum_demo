<objective>
Replace the integration harness's "every cycle ends in a Gold overwrite" liveness proof
before anything makes that assumption false.

Purpose: `tests/support/medallion_harness.py` documents, in the docstring of
`wait_for_new_gold_snapshot`, that a new Gold snapshot is the proof a deployment did
work — and `run_deployment` calls it unconditionally on every stage. GLD-01 (plan 04-05)
deletes that invariant. `gold_cutover.feature` walks three deployments over a lake whose
Silver deliberately does not change, so the moment the Gold skip lands the harness burns
90 s per stage and fails with `AssertionError: ... gained no snapshot within 90s`. That
feature is a **PR blocker** — `ci-m5-gates.yml` triggers on `iceberg/**`,
`tests/features/**` and `tests/support/**`. Landing the replacement one wave *before*
GLD-01 means the new signal is exercised by CI while it is still equivalent to the old
one, so a parser bug is caught before the behaviour change hides it.

The harness's own docstring already rejects the obvious alternative — waiting on a row
count returns immediately whenever a previous stage produced those rows. The replacement
is a per-cycle stdout marker, which also doubles as human-readable evidence in a log.
`ci-m5-gates.yml:41` starts only `minio` and `iceberg-rest`, so a PostgreSQL-backed
signal is not available to that job and is not used.

Output: `CYCLE_COMPLETE_MARKER` printed once per completed cycle;
`parse_cycle_marker`; `CycleWatcher`; `wait_for_cycle_complete`; `run_deployment`
switched over; `wait_for_new_gold_snapshot` removed.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| medallion subprocess stdout → test harness | A log line becomes the signal a deployment completed; a wrong or forged line would make a test pass falsely |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-12 | Spoofing | the stdout liveness marker | mitigate | The marker must be the **first** token of the line, is emitted from exactly one site, and carries the cycle id; `parse_cycle_marker` rejects lines that merely contain the token |
| T-04-13 | Denial of Service | piped stdout/stderr buffer | mitigate | `CycleWatcher` drains both pipes on daemon threads, removing a latent stall that already exists today because `run_deployment` never reads them |
| T-04-14 | Repudiation | a deployment that never ran passing as one that did | mitigate | No marker is printed for an aborted or early-returning cycle, and the watcher raises on timeout quoting the captured output |
| T-04-15 | Information disclosure | captured output in an assertion message | accept | Harness output can include medallion log lines. It runs only against a per-run isolated namespace with `METRICS_ENABLED=0`, and this is test-only output; the existing mismatch dump is not widened |
| T-04-SC | Tampering | npm/pip/cargo installs | accept | No package is installed in this plan |
</threat_model>
