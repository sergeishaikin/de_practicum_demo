<objective>
Measure the Arrow/Python boundary, then decide — on that measurement — whether it is worth
optimising now that the redundant full-state work is gone.

Purpose: PRF-01 is deliberately last and deliberately conditional. The locked instruction
is to optimise **only if still measurable** once the redundant work has been removed, and
to prefer an Arrow-native or vectorised implementation before considering anything else.
A result of "not worth doing" is a legitimate outcome and must be recorded rather than
forced into a code change.

Output: a one-off measurement script, a profile artifact carrying an explicit
disposition and the threshold that decision was made against, and — only if the
threshold is cleared — a vectorised change that preserves FF-14 exactly.

**PRF-01 must remain deliverable even if BENCH-01 is refused.** Plan 04-09's
authorisation gate sanctions refusal, in which case
`artifacts/phase-04/04-bench-summary.json` exists but carries
`disposition: "NOT MEASURED"` and no per-cycle durations. Task 2 therefore carries an
explicit branch for that case, defined here **before** the answer is known, so a
sanctioned refusal produces an honestly recorded PRF-01 rather than an undeliverable
one.

**Hard constraints.** No Rust, no new language, no new toolchain: explicitly out of scope,
and the Bronze writer question stays unmeasured-not-rejected, so nothing here may be
shaped to make reopening it easier or harder. FF-14 semantics must be preserved exactly:
the same `order_id` at the same `business_version` with a different business payload is a
**rejection**. That is a conflict detector, not an aggregation, and not a mechanical
`group_by`.
</objective>

  <action>
Add `scripts/profile_arrow_boundary.py`, following `scripts/verify_m5_cutover.py`'s shape:
a small module with a `main()` that takes arguments, prints nothing decorative and emits
JSON. `AGENTS.md` forbids adding a verification layer a change does not require; PRF-01
explicitly requires a measurement, and `scripts/` already holds exactly this kind of
one-off tool, so use that precedent rather than adding a pytest marker, a benchmark
plugin or a new runner.

Measure four steps separately, using the same call shapes the medallion actually uses:

1. **Arrow to Python** — `to_pylist()` on a delta Arrow table and on the current-Silver
   scan result;
2. **`collapse_delta`** on the resulting list of dicts;
3. **`resolve_against_current`** against a current-state list;
4. **Python to Arrow** — `_rows_to_silver` reconstruction of the resolved rows.

Generate synthetic rows matching the Silver schema. Sweep delta sizes across at least
four orders of magnitude — for example 1, 100, 10 000 and 1 000 000 rows — and record
the key cardinality and the overlap ratio with current state at each size, because the
cost of steps 2 and 3 depends on both. Report per-step wall time and per-step allocated
row counts, repeat each measurement enough times to report a median rather than a single
sample, and record the interpreter version, `pyarrow` version and host.

The script must not touch a catalog, a database, MinIO or Kafka. It measures pure
functions over synthetic data and must run in the default environment with no stack. If
that turns out to be impossible for any step, record which step and why, and measure the
rest.

Write `artifacts/phase-04/04-arrow-boundary-profile.json` in the `06-o1-summary.json`
style: `schema_version`, `phase`, `plan`, an environment block, a `measurements` array,
and a cross-reference to `artifacts/phase-04/04-bench-summary.json`.

State the limits of a synthetic microbenchmark next to its numbers: it does not reproduce
production cache behaviour, real payload distributions or the Arrow buffer layout a real
scan produces. It bounds the cost; it does not predict it.
  </action>

Write the decision down, and write the threshold **before** reading the answer against it.

Read `artifacts/phase-04/04-bench-summary.json` **first** and branch on its
`disposition`.

**Branch A — the benchmark was measured** (`disposition` is `PASS` or `INCONCLUSIVE`,
and per-cycle durations are present). State the threshold explicitly in the artifact:
the boundary is worth optimising only if its measured cost is a material share of the
measured post-change cycle at a delta size this pipeline plausibly sees. Name the share
and name the delta size, and justify both from `04-bench-summary.json` rather than
picking round numbers.

**Branch B — the benchmark was refused** (`disposition` is `NOT MEASURED`). The
threshold's normal denominator does not exist, and no substitute may be fabricated from
the pre-change baseline, which was produced by different code and cannot stand in for a
post-change cycle. Instead:

- record the missing input by name — `artifacts/phase-04/04-bench-summary.json`,
  `disposition: "NOT MEASURED"` — and quote its `reason`, so the cause reads as the
  operator's recorded refusal rather than an unexplained gap;
- set PRF-01's `disposition` to `NOT WORTH DOING (unmeasurable baseline)` if the
  measured boundary cost is negligible in absolute terms at every delta size the
  pipeline has actually been observed to produce, or to `INCONCLUSIVE` if it is not;
- derive the flip-point delta size from the **recorded production delta alone** — one
  key, one file, 4 422 bytes, from `artifacts/b2-rollout/06-o1-window.json` and
  `06-bounded-workload.json` — and say plainly that this bounds the question rather
  than answering it against a live cycle;
- do **not** change any code on this branch. An optimisation cannot be justified
  against a denominator that was never measured.

On both branches, record that the measured production delta in the whole recorded
evidence base is **one key, one file, 4 422 bytes** — so if the boundary only becomes
material at a size the pipeline has never observed, that is itself the finding.

Then compare and record `disposition` as one of:

- `NOT WORTH DOING` — the expected outcome given the recorded volumes. Record it with the
  numbers that support it and the delta size at which the conclusion would flip, so a
  future reader can re-open it with evidence instead of intuition. **This is a complete,
  successful outcome for PRF-01. Do not manufacture a code change to avoid it.**
- `OPTIMISE` — only if the threshold is genuinely cleared, and only on branch A.
- `NOT WORTH DOING (unmeasurable baseline)` or `INCONCLUSIVE` — branch B only, per the
  rules above. Both close PRF-01; neither is a failure.

If and only if the disposition is `OPTIMISE`, make the change in a **separate commit**
after the artifact is committed, and only as an Arrow-native or vectorised implementation
inside `iceberg/b2_spike.py`. In that case:

- FF-14 must be preserved exactly — same `order_id`, same `business_version`, different
  business payload must still raise. It is a conflict detector; a vectorised
  implementation that silently picks a winner is a correctness regression, not an
  optimisation;
- `tests/test_m5_fitness_functions.py` and
  `tests/features/silver_business_state.feature` must stay green unmodified, and
  `tests/test_b2_medallion.py`'s crash-before-commit and crash-after-commit recovery
  tests must stay green;
- add a test proving the vectorised path raises on the FF-14 case at each measured delta
  size, not only at size one;
- re-run the profile and record the after-numbers in the same artifact.

Add a short cross-reference note to `docs/adr/0002-steady-state-shadow-policy.md`
pointing at the profile artifact — the two together are the phase's answer to "where does
the remaining time go", and a reader arriving at the shadow-policy ADR should be able to
find the boundary measurement without searching. Do not restate the profile's contents
there.

Do not reopen the Bronze writer question, do not compare against any non-Python
implementation, and do not add a dependency.
  </action>
