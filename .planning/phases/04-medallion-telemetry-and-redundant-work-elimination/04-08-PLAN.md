<objective>
Answer, on the record, whether `SHADOW_COMPARE` must remain permanently enabled after a
successful cutover — and make the rollout matrix's four accepted states exactly assertable.

Purpose: the question has been open since M5 and has been answered informally as "yes,
keep it on" without stated conditions, which means nobody can tell whether the answer
would change and on what evidence. This phase produces the one piece of evidence that
actually moves the argument: with a receipt-gated fast path, a steady-state cycle over
unmoved state now performs no Bronze scan, no legacy rebuild and no comparison, so the
standing cost objection to permanent shadow validation largely evaporates. That changes
the shape of the answer and must be written down rather than assumed.

Output: `docs/adr/0002-steady-state-shadow-policy.md`, and a fitness assertion that the
matrix contains exactly its four accepted keys.

**Hard constraint, locked and non-negotiable.** This plan is analysis. Do **not** add
`(b2, persisted_silver, 0)` — or any other key — to `RUNTIME_ROLLOUT_MATRIX`. Do not
change `iceberg/common/cutover.py`. REGR-4 asserts the matrix is unchanged, and this plan
strengthens that assertion rather than relaxing it.
</objective>

  <action>
Write `docs/adr/0002-steady-state-shadow-policy.md` following ADR-0001's format: the same
header table (Status, Date, Deciders, Supersedes, Evidence base), then context, options,
decision, conditions and consequences.

An ADR rather than a remediation note, because the deliverable is a ratified policy with
conditions that a future change must satisfy — that is what an ADR is for, and ADR-0001
already governs the neighbouring decisions.

**Context.** State the question precisely: after a successful, evidenced cutover to
`GOLD_SOURCE=persisted_silver`, must `SHADOW_COMPARE` remain `1` forever? Record why it
was ever a question — a full Bronze scan, a full legacy Silver rebuild and a full
business-state comparison on every cycle. Record the measured cost from
`artifacts/b2-rollout/06-o1-window.json`, and record its limits verbatim: five cycles at
demo volume, one of which did real work, establishing **no scaling relationship
whatsoever**. Then record what this phase changed: with the receipt-gated fast path, a
cycle over unmoved Bronze and Silver under an unchanged runtime and projection contract
performs none of that work, so the cost argument now applies only to cycles that actually
have new state — which are exactly the cycles where validation is worth running.

**Options.** Evaluate all four locked candidates against the same criteria: permanent
shadow; change-triggered shadow; sampled or periodic shadow; and shadow disabled after a
certified cutover. For each, state what it costs, what it detects, what it stops
detecting, and what it does to rollback. Be specific about the failure mode each one
misses. Note in particular that "shadow disabled after a certified cutover" would require
the forbidden matrix key and would mean publishing business state that nothing validates
— and that the receipt-gated fast path is a strictly better version of the
"change-triggered" option, because it is triggered by proven state identity rather than
by a heuristic.

**Evidence and safety conditions.** This is the part the locked decision explicitly asks
for and the part that must not be hand-waved. State what would have to be true — as
checkable conditions, not sentiments — before any move away from the current policy could
be proposed: what evidence, over what window, at what volume, with what recovery drills
performed, with what rollback rehearsal, and with what alerting in place. Reference the
existing `evaluate_cutover_gate` checks as the precedent for expressing a gate as an
evaluable bundle, and say whether the steady-state conditions could be expressed the same
way. Do not implement such an evaluator here.

**Decision.** State it plainly, with its reasoning. Whatever the conclusion, state
explicitly that `RUNTIME_ROLLOUT_MATRIX` is **not changed by this ADR**, name the
forbidden `(b2, persisted_silver, 0)` combination, and say what would have to happen —
including who decides — before that could be revisited.

**Rollback.** Show that the chosen policy preserves the M4 rollback definition: rollback
changes the Gold source only and returns a cutover deployment to the `shadow` stage,
which is a state the matrix already accepts.

**Consequences and non-goals.** Include what this ADR does not decide. Where a claim
rests on reading code rather than on observed data, say so at the point of the claim, in
the style Phase 3 established.

Do not modify ADR-0001 in this plan — plan 04-05 already amended it, and a second editor
in the same phase would make the amendment history harder to read. Cross-reference it.
