<objective>
Create the arrival signal the freshness gate will read: a batch-load transaction
timestamp on the four `stg.*` tables, delivered as an additive idempotent
migration and replayed onto existing volumes through the established
`bootstrap_stack.py` path.

Purpose: `dbt source freshness` needs a `loaded_at_field`. `stg.*` has no
timestamp column that means "when this slice was loaded" — `ingest_date` is a
CSV column whose value is whatever the input file says. This plan creates the
signal and nothing else. No dbt config, no DAG task, no docs change yet.

Output: `db/init/008_stg_loaded_at.sql`, a `STG_LOADED_AT_MIGRATION` replay in
`scripts/bootstrap_stack.py`, and a fast-suite contract test that pins both plus
the fact that the ingestion path was not touched.
</objective>

  <action>
Create `db/init/008_stg_loaded_at.sql` with exactly four statements, one per
staging table, in the order `stg.orders`, `stg.order_items`,
`stg.order_payments`, `stg.customers`, each of the form
`alter table if exists <table> add column if not exists loaded_at timestamptz not null default now();`.
No index, no view, no data statement.

Precede them with a header comment that records, in this repository's voice,
three things a later reader must not have to rediscover:

1. This is a **batch-load transaction timestamp**, not literal row-arrival time.
   `now()` is transaction-start time and constant for the whole transaction, and
   `load_raw_csv_to_stg` wraps the truncate plus all four `COPY` calls in one
   `with _connect()` block, so one batch yields one identical value across all
   four tables by construction. `clock_timestamp()` would break that invariant
   and is deliberately not used.
2. `loaded_at` is deliberately absent from every CSV and from every `COPY`
   column list in `dags/warehouse_orders.py`, so PostgreSQL supplies the default
   on every load. The ingestion DAG needs no change.
3. The accepted false-fresh window: `ADD COLUMN ... NOT NULL DEFAULT now()`
   assigns the evaluated default to pre-existing rows too, so immediately after
   migration old staging rows report as freshly loaded. This is accepted, not
   fixed — the window is one ingestion run wide, the gate is only ever reached
   after `load_raw_csv_to_stg` truncates those rows, and the failure mode is a
   false pass rather than a false failure. A nullable transitional column or a
   sentinel timestamp is explicitly rejected.

In `scripts/bootstrap_stack.py`, add a module constant
`STG_LOADED_AT_MIGRATION = "/docker-entrypoint-initdb.d/008_stg_loaded_at.sql"`
immediately after `PIPELINE_PROVENANCE_MIGRATION`, and add a second
`_docker_exec("de-demo-postgres", "psql", "-X", "--set=ON_ERROR_STOP=1", ...)`

the `print("[OK] H1 bootstrap: ...")` line, passing `--file STG_LOADED_AT_MIGRATION`

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | `db/init/008_stg_loaded_at.sql` executed against a real warehouse | mitigate | DDL is additive and idempotent (`alter table if exists` / `add column if not exists`), contains no `insert`/`update`/`drop`, and is asserted comment-filtered by `test_stg_loaded_at_migration_is_additive_and_bootstrapped` |
| T-03-02 | Denial of service | `ALTER TABLE ... ADD COLUMN ... DEFAULT now()` table-rewrite lock | accept | `now()` is STABLE, so PostgreSQL 11+ stores it as a missing-value default without a rewrite; and `stg.*` holds one demo batch that is truncated before every load |
| T-03-03 | Repudiation | false-fresh window on pre-existing rows after migration | accept | Documented in the migration header and locked by CONTEXT: the window is one ingestion run wide, the gate is only reached after `load_raw_csv_to_stg` truncates, and the failure mode is a false pass, not a false failure |
| T-03-04 | Tampering | `psql --file` executed via `docker exec` | mitigate | Path is a module constant, not interpolated from input; `--set=ON_ERROR_STOP=1` is preserved; `_docker_exec` raises `RuntimeError` on non-zero return |
| T-03-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no packages and modifies no `requirements.in`, `requirements.txt`, `pyproject.toml`, or `uv.lock`; the CI stale-lock gate would fail if it did |
</threat_model>
