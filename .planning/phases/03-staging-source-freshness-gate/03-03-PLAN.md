<critical_facts>
VERIFIED in `03-RESEARCH.md` §Q2, §Q4. Not documentation claims.

1. **Exit codes on dbt-core 1.12.2.** `FreshnessStatus.Warn` is absent from the
   set counted by `GraphRunnableTask.interpret_results`, so warn → `success=True`
   → exit 0. `Error` and `RuntimeErr` are counted, so error → `success=False` →
   `ResultExit` → `ExitCodes.ModelError` = **1**. This is why no `sources.json`
   parsing fallback is needed and why the `warn_after` threshold is deliberately
   not separately asserted.
2. **An empty staging table ERRORS.** `max(loaded_at)` over an empty table is
   NULL, which `BaseAdapter._create_freshness_response` maps to
   `datetime(1,1,1)` — an age of ~2025 years. So `dbt source freshness` must
   never run before the seed, and must never be added to the mutation gate.
3. **The seed leaves staging seconds old.**
   `tests/fixtures/warehouse/seed_staging.sql` truncates and re-inserts with
   **explicit column lists** that never name `loaded_at`, inside one
   `begin;`/`commit;`. So PostgreSQL supplies one `now()` for all four tables and
   the rows are seconds old when freshness runs.
4. **The steps must go between the seed and `dbt build`.** Steps 6-8 of the job
   read only business columns; `10_rebuild_core.sql` and every model project
   named columns and never `select *` from `stg.*`. Inserting after step 9 or 10
   would put a stateful `update` next to the replay-parity `replay_check` schema
   and the many dbt invocations of the mutation gate, for no benefit.
5. **The mutation gate is indifferent — today.**
   `scripts/mutation_test.py` invokes only `dbt test --select <killer>` against a
   `copytree` copy of the project, never `dbt build` and never
   `dbt source freshness`; `dbt test` does not evaluate freshness. That is a
   property of today's mutation catalogue, not a guarantee, which is why the
   reset step is unconditional rather than relying on it.
6. **`db/init/008_stg_loaded_at.sql` applies automatically in this job.**
   `docker-compose.yml:31` mounts `./db/init` into
   `/docker-entrypoint-initdb.d`, the runner starts `de-demo-postgres` on a
   fresh volume, and `008` sorts after `007`. No `bootstrap_stack.py` call is
   needed here.
7. **GitHub's default `run:` shell is `bash -e`,** so a bare failing command
   aborts the step. The expected-failure idiom must be
   `if <cmd>; then echo …; exit 1; fi`, which suppresses `-e` for the condition
   and makes the inversion readable. This mirrors the existing
   `if [ -n "$violations" ]; then … exit 1; fi` pattern at `ci-pr.yml:121-125`.
</critical_facts>
