# S1.1 — historical `business_version` migration

Status: implemented; persistent-stack application is gated by read-only
classification and an explicit quiesce/recovery procedure.

## Evidence and rule

The persistent demo stack was profiled before any write. At the time of the
classification, all observed Bronze and Silver rows had `business_version IS
NULL`; every legacy `order_id` was a singleton; there were no duplicate
historical keys, no payload conflicts, and no overlap between legacy and
already-versioned observations.

The accepted rule is therefore:

```text
legacy singleton observation -> business_version = 1
```

This is a migration classification for a pre-M1 singleton entity. It is not a
calculation from `kafka_offset`, `kafka_partition`, event time, or file order.
The steady-state B2 comparator remains `business_version` only.

The migration fails closed if it sees duplicate legacy `order_id` values,
payload conflicts, a NULL `order_id`, or a legacy ID that also has a versioned
observation. No ambiguous row is assigned a synthetic version.

## Procedure

The procedure is [legacy_business_version_migration.py](../../iceberg/medallion/legacy_business_version_migration.py).
It first scans and profiles Bronze, validates the rule, then produces a new
Bronze image with only safe NULLs filled. Silver is reconciled from that image
through the shared `collapse_delta` B2 rule; it is not independently patched
row by row. Both writes include migration markers in snapshot summaries.

Run a dry-run first from the repository root (the live host profile is
illustrated below; the container uses the same script at `/app`):

```powershell
$env:ICEBERG_CATALOG_URI = 'http://localhost:18181'
$env:S3_ENDPOINT = 'http://localhost:19000'
$env:AWS_ACCESS_KEY_ID = 'minio'
$env:AWS_SECRET_ACCESS_KEY = 'minio123'
python iceberg/medallion/legacy_business_version_migration.py
python iceberg/medallion/legacy_business_version_migration.py --apply
```

The live migration must run with producers, Landing/Spark, Bronze writer, and
medallion quiesced. This gives the scan and overwrite one stable Bronze
boundary. Restart the services only after the apply output records both
snapshot IDs. New post-M1 events already carry `business_version=1` and are
handled by the normal pipeline after restart.

The command is idempotent: a second run sees zero NULL Bronze versions and
does not create another Bronze or Silver snapshot when Silver already equals
the B2 projection. If the process fails after Bronze commit and before Silver
reconciliation, rerunning is safe and completes the Silver step.

## Recovery and rollback

Before applying, record the dry-run output and stop the writers. Preserve the
pre-migration Bronze and Silver snapshot IDs until all dbt and E2E checks pass;
do not expire those snapshots during the verification window. If rollback is
required, stop ingestion again and use the Iceberg catalog's snapshot rollback
operation for each table to restore its recorded pre-migration snapshot, then
restart the pipeline. The migration markers and snapshot IDs provide the
reconciliation evidence for that operation.

Gold is not rewritten by S1.1 because assigning the domain baseline changes no
business dimension or measure. Verification compares Gold's logical rows
before and after and requires the same result.

## Verification

- Unit migration contract tests cover singleton classification, fail-closed
  duplicate/overlap handling, idempotency, and B2 projection.
- Live classification found an initial `208167` singleton legacy batch and a
  second `32`-row pre-M1 backlog released after restart. Both were migrated
  with zero duplicates, payload conflicts, or version-overlap IDs. The final
  stable stack had `208896` versioned Bronze rows and `208896` unique Silver
  rows.
- The post-apply dry-run reported `null_rows=0`, `bronze_changed=false`, and
  `silver_changed=false`.
- The persistent apply gate is: zero NULL versions in Bronze and Silver,
  global Silver uniqueness, no post-M1 version regression, unchanged Gold,
  all 26 dbt tests, and deterministic E2E.
- Persistent dbt verification: `26/26 PASS`.
- Stable Silver-derived Gold verification: `96` expected grains, `96` actual
  grains, `0` missing and `0` extra rows after rounding floating-point
  aggregates for comparison.
- D-3a, Gold ownership, B2 semantics, and observability are unchanged.
